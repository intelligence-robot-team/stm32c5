# 代码架构

> 本文件是设计基准。状态标记见 [README.md](README.md)。
> 截至 2026-11-27：**全部为设计，代码尚未落地**（v0.2 曾实现过一版骨架，已按要求回退，见 [修改日志.md](修改日志.md)）。

---

## 1. 设计目标与四条硬约束

1. **上层只依赖抽象基类和实例化对象**，不 include 任何具体型号头文件，不访问引脚。
2. **全工程只有 `bsp/board_init.c` 与 `bsp/board_config.h` 知道硬件映射**：哪个轮子挂哪个节点地址、用哪条总线、什么传动比。
3. **具体外设子类以 `static` 声明在 `board_init.c` 内部**，初始化后向上转型为基类指针，通过 `g_motor[]` 暴露。
4. **未确认的内容不写进代码**：要么做成 `board_config.h` 的可配置占位项，要么进 [待确认问题.md](待确认问题.md)。

## 2. 分层与依赖

```
        APP        app_init / chassis_drive_task / command_task / motion_control_task / protocol
         │         任务、指令接收、仲裁、超时、调度
         ▼
       MODULE     mecanum（运动学）/ motion（闭环）/ algorithm（PID、滤波）
         │         只做数值计算，不认电机、不认总线
         ▼
       DEVICE     motor（基类 + CAN 基类 + ZDT 子类）/ imu（待型号确认）
         │         只调 Platform，不直接调 HAL
         ▼
      PLATFORM    platform_can / platform_time
         │         唯一 include HAL 的业务层
         ▼
       HAL / 硬件

   BSP 旁挂：board_init.c 由启动钩子调用，创对象 → 配参数 → 交句柄，不参与运行时调用链
```

规则：

- 依赖只能向下，不允许 MODULE 反向 include APP。
- **MODULE 只做纯计算**：`mecanum` 输入速度输出轮速，`motion` 输入目标与反馈输出速度，`algorithm` 提供 PID 与滤波，三者互不依赖。
- **APP 负责组装**：谁调用谁、按什么顺序、什么时候超时，都在 app 层决定，module 里不出现任务、延时、队列。
- 例外并记录在案：`app/chassis_drive_task.c` 直接持有 `Motor*` 并调用 `Motor_SetSpeed()`，因此 APP 会 include `device/motor.h`。这是按当前目录结构（没有独立的"底盘执行"模块）做的取舍，见 S-10。

## 4. 对象模型

### 4.1 继承链

```
Motor                    基类：ops + 公共状态（index / node_id / online / fb）
  └─ Motor_CAN           中间基类：+ bus
       └─ Motor_StepperZDT  具体子类：+ 轮径 / 传动比 / 加速度 / 方向取反
```

为什么需要 `Motor_CAN` 这一层：

- 它承载"挂在一条 CAN 总线上、有节点地址"这个共性，未来加第二种 CAN 电机（伺服、另一家步进）时只继承它，不重复写发送逻辑。
- 它不绑定 Ops 表，因为不同电机的协议不同；Ops 由最底层子类绑定。
- 代价是多一层 `container_of` 路径（`base.base`），可接受。

### 4.2 Ops 表与多态

```c
typedef struct {
    bool (*SetSpeed)(Motor *self, int32_t speed_mm_s);
    void (*Stop)(Motor *self);
    bool (*Enable)(Motor *self, bool enable);
    bool (*RequestFeedback)(Motor *self);
    bool (*ReadFeedback)(Motor *self, MotorFeedback_t *out);
} MotorOps;

struct Motor {
    const MotorOps *ops;   /* 子类 Init 时绑定 */
    ...
};
```

上层永远只写 `Motor_SetSpeed(g_motor[i], v)`，不写函数指针、不判断型号。

### 4.3 向下转型

ZDT 子类的实现里需要访问自己的私有成员，用 `container_of`：

```c
static bool zdt_set_speed(Motor *motor, int32_t speed_mm_s)
{
    Motor_StepperZDT *self = container_of(motor, Motor_StepperZDT, base.base);
    ...
}
```

注意两点：

- 只能对真实子类对象中的对应基类成员转换；
- 两级继承时成员路径写全（`base.base`），`offsetof` 支持嵌套成员。

### 4.4 单位约定

| 层 | 单位 | 说明 |
|---|---|---|
| 上层 / 底盘 | mm/s（`int32_t`，带符号） | 轮端线速度，正值表示车前进方向 |
| ZDT 速度帧 | 0.1 RPM（`uint16_t`） | 换算：`raw = |v| × 600 / (πD)` |
| ZDT 位置帧 | 0.1°（X 固件） | 一圈 3600 计数，`counts_per_rev` 可配 |
| 航向 / 角度 | rad，`[-π, π]` | 与 ROS REP-103 一致 |

换算全部封在子类里。底盘层如果出现 `rpm` 这个词，就是分层被破坏了。

## 5. 数据结构

### 5.1 电机反馈（`motor.h`）

```c
typedef struct {
    int32_t counts;          /* 位置原始计数，带符号 */
    float   counts_per_rev;  /* 一圈计数，供上层换算 */
    float   distance_mm;     /* 累计位移，子类已按传动比换算 */
    float   speed_mm_s;      /* 实际轮端线速度 */
    uint8_t fault;           /* 故障位，0 正常；bit7 = 命令被拒 */
    bool    valid;           /* 是否收到过位置反馈 */
} MotorFeedback_t;
```

`Motor` 基类里保存一份 `fb` 缓存，`ReadFeedback` 拷贝出去，避免上层拿到会被中断改写的指针。

### 5.2 底盘三件套（共享结构体，位置待定 S-14）

```c
Chassis_Command_t    /* 写：command_task   读：motion_control_task */
  seq / type / source / vx,vy,wz / distance / heading / target x,y / stamp / valid

Chassis_Velocity_t   /* 写：当前 owner  读：chassis_drive_task */
  vx, vy, wz, stamp_ms

Chassis_Feedback_t   /* 写：chassis_drive_task 读：command_task、motion_control_task */
  encoder[4] / wheel_mm_s[4] / yaw / yaw_rate / vx,vy,wz / odom / status / fault
```

三者都不放进全局大结构体，写入者唯一，具体同步机制见第 9.3 节。

**结构体放哪里**（S-14）：新目录里没有独立的 `chassis` 模块，三个结构体被 `app` 与 `module` 同时使用，位置需要先定，否则容易出现 `module` 反向 include `app`。当前候选：

1. 放 `module/motion/motion.h`，`mecanum.h` 只定义轮速与几何 —— 依赖方向 `motion → mecanum`，无环；
2. 单独建 `module/chassis_types.h` —— 最清晰，但多一个文件；
3. 放 `app/` —— 不推荐，`module` 会依赖 `app`，破坏分层。

倾向方案 2：一个头文件、无反向依赖，成本最低。

## 6. 启动流程

```
main()                          CubeMX 生成，保持不动
  └─ mx_system_init()           CubeMX 生成：时钟、MPU、NVIC 分组、外设初始化
       └─ post_system_init_hook()     __WEAK，由 app/app_init.c 覆盖
            ├─ Board_Init()           创建 4 个 static 电机对象、启动 CAN、向上转型
            └─ App_Init()             计划：创建任务与协议对象
  └─ while (1) {}               调度器尚未启动
```

为什么不用 `main.c`：

- `main.c` 是 CubeMX 生成文件，没有 USER CODE 保护段，重新生成会覆盖。
- `mx_system.c` 里的 `post_system_init_hook()` 是专为此预留的弱函数，语义上仍属 main 的启动流程。

例外说明：`app_init.c` 是全工程唯一包含 `mx_system.h` 的 APP 文件。它只声明启动入口，不包含引脚或寄存器操作。

后续任务落地后的顺序应为：`Board_Init → Module_Init → App_Init（创建任务）→ vTaskStartScheduler()`。任务层落地前调度器不启动，主循环停在 `main.c` 的 `while(1)`。

## 7. Platform 层取舍（ADR-01）

**结论：保留，但只做轻量封装，三个文件、约 250 行。**

| 方案 | 做法 | 成本 | 换芯片的影响面 |
|---|---|---|---|
| A 完整抽象 | 通用 handle、DMA、回调、GPIO 全部包一层 | 上千行，且要发明跨芯片类型 | 只改 platform，但抽象本身容易漏 |
| **B 轻量（采用）** | 只包"总线"和"时间"：枚举 + 缓冲区指针，不暴露 `hal_*_handle_t` | 约 250 行 | **只改 2 个 .c**，Device 及以上不动 |
| C 不引入 | Device 直接调 HAL | 0 行 | 每个设备子类都要按芯片改写，成本随设备数线性增长 |

选择 B 的理由：

1. 迁移成本是**常数**，不是随设备数增长。换到 STM32F4/H7 只需重写 `platform_can.c` 与 `platform_time.c`。
2. 不发明通用类型。接口里只有 `PlatformCanBus_t` 这种板级无关的枚举，和 `uint8_t*` 缓冲，任何芯片都能实现。
3. 成本可控。`platform_can.c` 只做四件事：取句柄、启动、发帧、收帧入环。

不做的部分：

- **不抽象 GPIO / PWM / 编码器**：当前一个都没配置，先建空壳属于过度设计。等真正用到时再按同一模式加，影响面仍然只在 platform 目录。
- **不在 Platform 里做协议解析**：那是 Device 的职责。
- **不在 Platform 里创建 FreeRTOS 对象**：接收用无锁环形缓冲（单生产者中断 / 单消费者任务），Platform 保持 RTOS 无关，裸机也能用。

代价（明确承认）：

- 多一层函数调用，每条 CAN 帧多几微秒，对 5 ms 周期无影响。
- `platform_can.c` 里仍然出现 `FDCAN1_IT0_IRQn` 这类芯片名字——这是**芯片差异**，属于 Platform 的职责；**板级差异**（哪条总线接电机）不在这里，在 BSP。

## 8. 硬件映射的唯一入口

`bsp/board_config.h` + `bsp/board_init.c` 是唯一允许出现下列信息的地方：

- 四条总线/四个节点地址的对应关系；
- 轮径、每圈计数、加速度、方向取反；
- 电机挂在 CAN1 还是 CAN2；
- IMU / 上位机 / 遥控接哪个串口（目前全是 0 占位）。

计划在 `board_init.c` 中写成：

```c
static Motor_StepperZDT s_motor[BOARD_MOTOR_COUNT];   /* 具体子类，仅本文件可见 */

Motor *g_motor[BOARD_MOTOR_COUNT];                    /* 向上转型后的句柄 */

void Board_Init(void)
{
    Platform_CAN_Init(BOARD_MOTOR_BUS);
    for (i...) Motor_StepperZDT_Init(&s_motor[i], BOARD_MOTOR_BUS, node_id[i], i, &cfg[i]);
    for (i...) g_motor[i] = &s_motor[i].base.base;    /* 向上转型 */
}
```

换电机型号时只改这三行：`s_motor` 的类型、`Init` 函数、参数表。上层一行不动。

**两个必须说明的例外**：

1. `platform_can.c` 知道"这颗 MCU 有 FDCAN1/FDCAN2"，这是芯片映射，不是板级映射。
2. `generated/hal/*.c` 知道引脚与复用功能，那是 CubeMX 的职责。

## 9. 后续模块设计（未实现）

### 9.1 任务划分

| 任务 | 周期 | 职责 | 优先级 |
|---|---|---|---|
| `chassis_drive_task` | 5 ms 固定 | 取速度快照 → `Mecanum_InverseKinematics` → 下发四电机 → 读反馈 → 更新里程计 → 发布 Feedback | 最高 |
| `motion_control_task` | 5 ms | 调 `Motion_Update()`，把目标位姿与反馈算成整车速度 | 次高 |
| `command_task` | 事件驱动 + 20 ms 回传 | 解析指令、申请控制权、更新指令、超时停车、组帧回传 | 普通 |

说明（见 S-12）：

- 运动闭环已明确为独立的 `motion_control_task`，不再并入底盘任务，S-11 关闭。
- `command_task` 的名称是通用的，但描述写的是"底盘通讯"；`arm_protocol` 仍保留。机械臂指令由谁接收、机械臂执行层（设备、状态机）如何组织，尚未定义。

`chassis_drive_task` 每周期还需要调用 `Board_PollCan()` 把 CAN 帧分发到各电机，并按 50 Hz（不是每 5 ms）调用 `Motor_RequestFeedback()`。

### 9.2 数据流

```
上位机 / 遥控
   │
   ▼
command_task ── 速度模式 ──────────────────────────────┐
   │                                                   │
   └─ 距离/位姿指令 → Chassis_Command_t                 │
                          │                            │
                          └→ motion_control_task ──────┤
                                                       ▼
                                        仲裁 + 超时（app）→ 速度快照 → chassis_drive_task
                                                                          │
                                                          4 × Motor ←─────┤
                                                                          ▼
                                              command_task ← Chassis_Feedback_t
```

### 9.3 并发与所有权

| 数据 | 唯一写者 | 读者 | 机制 |
|---|---|---|---|
| `Chassis_Command_t` | Comm | Motion | 短临界区整体拷贝 + `seq` |
| `Chassis_Velocity_t` | 当前 owner（Comm 或 Motion） | Chassis | 写入前 owner 校验 + 时间戳老化 |
| `Chassis_Feedback_t` | Chassis | Comm、Motion | 双缓冲 + 序号 |
| 电机原始帧 | CAN 中断 | Chassis | 环形缓冲，任务内解析 |

速度老化是关键安全属性：速度指令带时间戳，5 ms 任务检查，超时自动归零，不依赖通讯任务存活。

### 9.4 运动学

```
k = L + W（L 半轴距，W 半轮距）
v_FL = +vx − vy − k·wz     v_FR = +vx + vy + k·wz
v_RL = +vx + vy − k·wz     v_RR = +vx − vy + k·wz
```

`Mecanum_InverseKinematics()` 放在 `module/mecanum/`，保持纯函数、无状态，便于单独测试。

## 11. 与 `skill.md` 的偏离

| 编号 | 偏离 | 理由 | 可回退方案 |
|---|---|---|---|
| D-1 | 启动不写在 `main.c`，写在 `post_system_init_hook()` | 生成文件会被覆盖 | 接受覆盖风险可改回 `main.c` |
| D-2 | `Motor_SetSpeed` 参数单位为 mm/s | 上层只出现物理量，驱动器单位封在子类 | 可改原生单位，但底盘要认识型号 |
| D-3 | 新增 `Motor_CAN` 中间基类 | 承载"总线 + 节点地址"共性，避免第二个 CAN 电机重复实现 | 可合并进子类 |
| D-4 | 新增 `platform_time` | DEVICE 需要超时判断，不能直接调 `HAL_GetTick` | 可去掉，DEVICE 直接调 HAL |
| D-5 | 不设 `module/control`，控制权仲裁放在 `app` | 按最新目录要求，仲裁属于业务流程；单列模块会让 app 与 module 职责重叠 | 若后期发现仲裁逻辑变复杂，再抽回 module |
| D-6 | 不建 `platform_gpio` | 当前无 GPIO 需求，避免空壳 | 有 DIR/EN/急停后再加 |
| D-7 | `vApplicationStackOverflowHook` 放 APP 层 | 属于系统级钩子，与业务无关 | 可放 `bsp/` |

## 12. 新增一种设备的标准步骤

以 IMU 为例（型号确认后照此执行）：

1. `device/imu/imu.h`：定义 `IMU` 基类、`ImuSample_t`、`ImuOps`（Start / Read / Calibrate）。
2. `device/imu/imu_xxx.c`：具体子类，绑定 Ops，用 `container_of` 还原自身。
3. 若需要串口：先加 `platform_uart.c`（同样只暴露端口枚举与缓冲区），再加设备子类。
4. `bsp/board_config.h`：加型号相关的可配置项（端口、波特率、安装方向）。
5. `bsp/board_init.c`：加 `static IMU_Xxx s_imu;`，初始化后赋给 `IMU *g_imu;`。
6. `cmake/user.cmake`：登记新源文件与头文件目录。
7. 更新 [修改日志.md](修改日志.md) 与 [待确认问题.md](待确认问题.md)。

上层（底盘/任务）只 include `imu.h`，拿 `g_imu`。
